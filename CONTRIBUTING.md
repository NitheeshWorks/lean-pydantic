# Contributing to lean-pydantic

`README.md` covers usage. This file covers the architecture, the verification
rules, the repository layout and the conventions, and is the document to keep
current when the code changes.

## Architecture

`LeanPydantic/` is layered bottom-up; each layer imports only the ones below it, so a
proof at one layer rewrites with lemmas from beneath it instead of unfolding
to bytes:

| Directory | Holds | Proved? |
|---|---|---|
| `DataTypes/` | structures and inductives; invariants are fields | n/a |
| `RepoImpl/` | executable definitions; total, structural recursion | subject of proofs |
| `Specifications/` | the properties, in `Prop` | the contract |
| `Proofs/` | theorems; `Proofs/Verified.lean` bundles one `Verified<Layer>` per layer | yes |
| `APIs/` | the public surface, returning refinements | by construction |
| `Transport.lean` (if present) | the only effectful module | no; tested |

Everything except the transport module is a pure function. This is
load-bearing: a round-trip property of a function is an equation that
`omega` and `simp` attack directly; the same property of a procedure would
be a Hoare triple over a heap.

## Verification <a name="verification"></a>

* **Weak preconditions, strong postconditions.** A public function takes the
  minimal hypothesis its body needs (usually none; the refinement lives in the
  input type) and returns the strongest useful statement, typically a round
  trip or a membership, as `{r // Post r}` or `Except Err {r // Post r}`.
* **Refinement types are subtypes with `Decidable` predicates**, so the same
  predicate is checked at runtime (`if h : P x`) and used in proofs.
* **Totality.** No `partial def` or `unsafe` under `LeanPydantic/`; all
  recursion is structural.
* **`_ext` lemmas.** A decoder lemma holds on any continuation of the buffer and
  reports the final position, so field lemmas compose. Do not add a lemma that
  only holds at the end of a buffer; it is unusable one field later.
* **Numbers.** `Nat`/`Int`/decimal-as-rational in proofs. `Float` only at the
  boundary via `Float.toBits`. Never `bv_decide` or `native_decide`.
* **The gate.** `scripts/check.sh` runs what CI runs: build, `sorry` grep,
  `scripts/Axioms.lean` (every theorem under `LeanPydantic` reaches only `propext`,
  `Quot.sound`, `Classical.choice`), `lake exe props`, `lake exe conformance`,
  the traceability check.

### Where the proofs come from

* `Proofs/Number.lean`: one lemma, `Num.rel_at` (a scale-invariant relation
  reads the same at any common lower exponent), and its instances for `<`,
  `≤`, `∣`. `Denotes` connects a JSON number, the decimal it validates to and
  a bound as the schema prints it.
* `Proofs/Constraint.lean`: pydantic-order validation from Keel's
  `validate_iff`; keyword soundness by one induction over the constraint,
  from each carrier's `LawfulConstrained` instance.
* `Proofs/Scalars.lean`, `Proofs/Wrappers.lean`: each scalar's laws by case
  analysis on the JSON value; `Option` and refinements inherit them.
* `Proofs/Fields.lean`: `nil_lawful` and `field_lawful`. A model's laws are a
  chain of these, written by `deriving Model` (`APIs/Derive.lean`), with
  each field-name freshness side condition closed by `decide`.
* `APIs/Model.lean`: the public equations (`model_validate_model_dump`,
  `schema_sound`, `model_dump_conforms`, `validate_loc_prefix`).

### Canonical constraints

Keel stores each atom's `Ordered`/`Divisible`/`Sized`/`Textual` instance in
the atom, so `@Constraint.gt Int weird 0` would mean something other than
`gt 0`. The keyword soundness theorem assumes atoms built with the carrier's
own instances (`Constrained.Std`), and the refinement's `LawfulJson`
instance asks for `Canonical c`, which instance resolution supplies for any
constraint written in the notation.

### Tested, not proved

Listed here with the reason, and in `docs/traceability.toml` with
`status = "tested"`.

* **Lax coercions** (`Coerce.strAsInt`, `strAsFloat`, `strAsBool`,
  `Scalar.bool`): a rule-for-rule port of pydantic-core's `shared.rs`. There
  is no independent specification to prove them against; the specification
  is pydantic's behaviour, so they are checked against it byte for byte
  (`tests/ConformanceTable.lean`, generated by
  `scripts/conformance/generate.py` from the released pydantic) and by
  properties.
* **Error JSON layout** (`ValidationError.json`, `ErrorDetails.toJson`): a
  formatting question, checked byte for byte against pydantic.
* **The JSON-text round trip** (`model_validate_json (model_dump_json a)`):
  it rests on lean-json's `from_json_to_json`; tested in `Props`.

### Deviations from upstream

* `Decimal` is pydantic's `FiniteFloat`, held exactly: no IEEE rounding, no
  `float` tolerance in `multiple_of`, and huge literals keep their value
  (pydantic: `inf`). NaN and the infinities are `finite_number`. Plain
  `float` (`allow_inf_nan=True`) is not provided yet.
* A constraint given twice must hold both times (pydantic keeps the last);
  the schema keeps pydantic's last-wins keyword.
* Field titles use ASCII case mapping.
* Matched on purpose although upstream is wrong: UP-032 (`'0-5'` is `-5`),
  UP-033 (`int_parsing_size` message on floats), UP-034 (`NaN` in
  `ValidationError.json()`).
* With `open LeanPydantic`, `a ∣ b` for an identifier `b` reads as a
  refinement, not divisibility (the notation outranks core's `∣` so that
  `Nat ∣ le 100` never becomes a divisibility claim).

## Tests

* `tests/Props.lean`: seeded property tests, no dependencies, under a second.
* `tests/Conformance.lean`: cases re-expressed from the upstream suite; each
  names the upstream test (`tests/test_x.py::test_y`).
* `tests/pbt/`: a separate Lake package, the one place an external dependency
  (`plausible`) is taken.

## Traceability

`docs/traceability.toml` links upstream behaviour to the Lean symbol, theorem
and test that realise it. Add a row when behaviour is newly implemented,
tested-only, excluded, or deviates. CI fails if a registered symbol does not
resolve.

## Conventions

* Lean 4 `leanprover/lean4:v4.35.0`; no Mathlib; the core library depends only on Lean
  core and the sibling `lean-*` repos listed in `lakefile.toml`, pinned by
  commit in `lake-manifest.json`.
* Choose the definition that suits the automation over a prettier one with a
  harder proof.
* No upstream code is copied; the upstream test suite and docs are the spec.
